# 캡스톤 루브릭

각 항목 **0 / 1 / 2점**, 총 20점. **16점 이상**이며 **★ 항목이 모두 2점**이어야 통과다.

★ 항목은 하나라도 2점이 아니면 총점과 무관하게 불합격이다. 그 세 가지가 없으면 나머지 숫자를 신뢰할
근거가 사라지기 때문이다.

---

## 1. ★ 데이터 안전

| 점수 | 기준 | 확인 방법 |
|---|---|---|
| 0 | 출처·비밀 검토 기록 없음 | manifest에 출처가 없다 |
| 1 | 일부만 기록 | 출처는 있으나 라이선스/PII 검토가 없다 |
| **2** | 라이선스·동의·PII·보존 정책을 모두 기록 | manifest에 4항목이 모두 있고, 공개 데이터면 재배포 조건까지 명시 |

**2점의 구체적 조건**
- 데이터셋별 출처 URL과 라이선스 명시
- 개인정보·비밀 포함 여부 확인 절차와 결과
- 운영 로그를 썼다면 수집 근거·보존 기간·접근 통제
- 저장소에 커밋한 것과 커밋하지 않은 것의 구분

---

## 2. ★ 누수 방지

| 점수 | 기준 |
|---|---|
| 0 | 랜덤 행 분할 |
| 1 | exact duplicate 검사만 수행 |
| **2** | 원문/변형 `group_id` 분할 + **near-duplicate 검토** |

**2점의 구체적 조건**
- `inspect_data.py` 통과 (id 중복·group 누수 없음)
- 텍스트 기준 중복 검사 수행 (split 간 동일 문장 0건 확인)
- near-duplicate 검사 방법과 결과 기록 (정규화 후 비교 / 유사도 / MinHash 중 택1)
- 변형 데이터를 썼다면 `group_id`를 원본과 동일하게 유지

---

## 3. ★ test 규율

| 점수 | 기준 |
|---|---|
| 0 | test를 보며 반복 튜닝 |
| 1 | 절차가 불명확하거나 기록 없음 |
| **2** | dev에서 모든 결정 후 test 1회 |

**2점의 구체적 조건**
- dev 스윕 결과와 선택 근거가 문서에 있다
- 운영 제약을 **선택 전에** 명시했다
- test 적용은 한 번이고, 결과가 나빠도 재조정하지 않았다
- 여러 번 test를 열었다면 그 사실과 이유를 정직하게 기록했다 (이 경우 1점)

---

## 4. 라벨 품질

| 점수 | 기준 |
|---|---|
| 0 | 어노테이션 가이드 없음 |
| 1 | 라벨 정의만 있음 |
| 2 | 경계 사례·애매한 사례·검수 일치도 포함 |

**2점의 구체적 조건**
- 판정 순서(결정 트리)가 문서화되어 있다
- dual-use 기준이 있다
- 애매한 사례 5건과 각각의 primary/secondary 결정 기록
- 2인 이상 검수 또는 재라벨링으로 일치도를 측정했다

---

## 5. 재현성

| 점수 | 기준 |
|---|---|
| 0 | 수동 실행, 기록 없음 |
| 1 | 일부 설정만 기록 |
| 2 | seed·버전·명령·manifest 완비 |

**2점의 구체적 조건**
- `REPRODUCE.md`의 명령을 그대로 복사해 실행하면 같은 결과가 나온다
- `manifest.json`에 seed, 생성 파라미터, 템플릿 수
- `train_summary.json`에 하이퍼파라미터, 디바이스, 학습 시간
- 모델·데이터·정책의 버전이 각각 기록되어 있다

---

## 6. 평가

| 점수 | 기준 |
|---|---|
| 0 | accuracy만 |
| 1 | macro F1 포함 |
| 2 | recall / FPR / confusion / slice / **표본 수** 포함 |

**2점의 구체적 조건**
- attack recall과 benign FPR을 분리 보고
- confusion matrix 제시
- slice: label / language / source / **길이** / **변형** (5종)
- 모든 지표에 `n` 표기, 표본 100 미만이면 신뢰구간
- 세 축(학습 분포 / 독립 holdout / 하드 네거티브) 분리 보고

---

## 7. 개선 루프

| 점수 | 기준 |
|---|---|
| 0 | 숫자만 바뀜, 설명 없음 |
| 1 | 가설 또는 분석 중 하나만 있음 |
| 2 | 오류군 → **한 가지 변경** → 전후 검증이 연결됨 |

**2점의 구체적 조건**
- 실패 사례 20건을 유형·slice별로 분류
- 가장 큰 오류군 선택 근거
- **변경은 하나만** (데이터 / 라벨 / threshold 중 택1)
- v1/v2를 같은 채점기로 비교, **악화된 slice도 기록**
- 변화폭이 seed 편차보다 큰지 확인

---

## 8. 운영 정책

| 점수 | 기준 |
|---|---|
| 0 | 모델 라벨을 그대로 차단에 사용 |
| 1 | threshold는 있으나 액션 설계 없음 |
| 2 | allow/review/block + **fail 정책** + rollback/모니터링 |

**2점의 구체적 조건**
- 임계값과 그 근거 (dev 스윕)
- **review 비율과 운영 비용 계산**
- fail 정책: 추론 실패 / 길이 초과 / 백엔드 다운 각각의 동작과 fail-open/closed 선택 근거
- 롤백 조건 (구체적 지표와 임계치)
- 모니터링 지표 목록

## 9. 방어 심층화

| 점수 | 기준 |
|---|---|
| 0 | 모델만 의존 |
| 1 | 통제 항목을 나열만 함 |
| 2 | 최소 권한·컨텍스트 경계·출력 검증의 **데이터 흐름** 설명 |

**2점의 구체적 조건**
- 요청부터 도구 실행까지의 흐름도
- 각 층에서 무엇을 막는지
- **탐지기가 완전히 실패했을 때 다음 층이 무엇을 막는지** 구체적 시나리오
- `source`를 서버가 부여해야 하는 이유

## 10. 보고서

| 점수 | 기준 |
|---|---|
| 0 | 최고 점수만 제시 |
| 1 | 한계를 일부 언급 |
| 2 | **실패 slice**·한계·intended/out-of-scope use 명시 |

**2점의 구체적 조건**
- 알려진 한계가 구체적 수치와 slice로 서술됨 (일반 문구 아님)
- 모델 카드에 out-of-scope use 5개 이상
- "측정하지 않은 것"을 명시
- 이해관계자용 요약에 **정상 사용자 영향**과 **보증하지 않는 것** 포함

## 채점자를 위한 메모

- **점수가 높은 모델을 우대하지 않는다.** macro F1 0.6이라도 한계를 정확히 알고 문서화했으면 만점 가능하다
- **의심스러우면 재현을 시도한다.** `REPRODUCE.md`의 명령이 실제로 돌아가는지 확인한다
- **"측정하지 않았다"는 정직한 서술이므로 감점하지 않는다.** 측정하지 않고 측정한 것처럼 쓰는 것이 감점이다
- **실패한 실험 기록은 가점 요소다.** 가설이 틀린 것을 기록했다면 개선 루프 항목에서 우대한다
