# 05 · 독립 벤치마크와 보안 모델 리포트

## 이 레슨을 마치면

- 벤치마크를 **세 축**으로 나눠 보고해야 하는 이유를 안다.
- 표본 수와 신뢰구간 없는 숫자가 왜 위험한지 계산으로 안다.
- 좋은 리포트와 나쁜 리포트의 차이를 구체적 항목으로 구분한다.
- 문서와 코드가 어긋나는 문제(드리프트)를 인지하고 대비한다.

---

## 1. 벤치마크는 하나가 아니다

"macro F1 0.837"이라는 숫자 하나로는 아무것도 알 수 없다. **어느 분포에서 잰 것인가**가 빠져 있기 때문이다.

세 축으로 나눠 재고, 나눠 보고한다.

| 축 | 내용 | 이 커리큘럼에서 | 무엇을 말해주는가 |
|---|---|---|---|
| **학습 분포 안** | 같은 생성기, 다른 템플릿 | `runs/data/v1/test.jsonl` | 학습이 제대로 됐는가 |
| **독립 holdout** | 다른 방법으로 만든 검수 데이터 | `common/data/bench/gold.jsonl` | 일반화가 되는가 |
| **정상 운영 분포** | 실제 트래픽 대리 | (합성만으로는 불가) | 실제로 쓸 만한가 |

세 숫자의 **차이**가 정보다. 하나로 합치면 그 차이가 사라진다.

우리 실측(모두 `mbert-v1` 기준):

| 축 | n | macro F1 | attack recall | benign FPR |
|---|---:|---:|---:|---:|
| 합성 test | 192 | 0.750 | 0.914 | 0.328 |
| 독립 bench | 24 | 0.837 | 0.938 | 0.250 |
| 하드 네거티브 전용 | 8 | — | — | **0.375** |
| 운영 분포 | 0 | — | — | — |

세 번째 행이 가장 나쁘다. **공격 어휘를 포함한 정상 문장에서 오탐률이 가장 높다.** 전체 평균(0.328)이나
독립 벤치(0.250)만 보면 이 사실이 드러나지 않는다. 하드 네거티브를 별도 축으로 두는 이유가 이것이다.

마지막 줄이 비어 있는 것이 정직한 상태다. **"측정하지 않았다"를 "측정할 필요 없다"로 바꾸지 않는다.**

참고 프로젝트(`sgt-owasp`)도 FPR을 세 개로 나눈다: 학습 분포 안(`salmon_safe_fpr`), 도메인
홀드아웃(`holdout_fpr`), 실고객 대리(`probe_fpr`). 이름이 다를 뿐 같은 사고방식이다.

## 2. 표본 수 없는 숫자는 숫자가 아니다

우리 독립 벤치는 24건이다. 한 건이 **4.2%**다.

```text
정상 8건 중 2건 오탐 → benign FPR 0.250
정상 8건 중 1건 오탐 → benign FPR 0.125
```

**한 건 차이로 FPR이 절반이 된다.** 이 정도 표본에서 "0.250 → 0.125로 개선했다"는 주장은 근거가 약하다.

### 신뢰구간을 대략 계산해 보자

비율의 95% 신뢰구간은 정규 근사로 이렇게 잡을 수 있다(작은 표본에서는 부정확하지만 감을 잡는 데는 충분하다).

```text
p ± 1.96 × √(p(1-p)/n)

n=8,   p=0.250  →  0.250 ± 0.300  →  [0.00, 0.55]   ← 거의 아무 정보가 없다
n=64,  p=0.250  →  0.250 ± 0.106  →  [0.14, 0.36]
n=640, p=0.250  →  0.250 ± 0.034  →  [0.22, 0.28]
```

n=8에서 잰 FPR 0.250은 **실제로는 0%일 수도 55%일 수도** 있다는 뜻이다.

참고 프로젝트가 "정확도 97.5%"라고 보고할 때 괄호에 **"40개 테스트 케이스 기준"**을 붙이는 이유다.
40건이면 한 건이 2.5%다. 97.5%는 "39/40"이고, 한 건만 더 틀리면 95%다.

> **원칙** — 지표를 쓸 때는 **항상 `n`을 함께** 쓴다. 표본이 100건 미만이면 신뢰구간도 함께 쓴다.

## 3. 좋은 리포트의 구성

```bash
python 03-advanced/05-benchmark-and-report/make_report.py \
  --reports runs/models/mbert-v1/test-report/report.json \
            runs/models/mbert-v1/bench-report/report.json \
  --latency runs/latency.json \
  --out runs/report/model-report.md
```

생성되는 것은 **뼈대**다. 나머지는 사람이 채운다.

| 섹션 | 자동 생성 | 사람이 채울 것 |
|---|---|---|
| 성능 요약 | ✅ 표 | 표본 수 해석, 신뢰구간 |
| 지연시간 | ✅ JSON | 측정 조건, 제외한 것 |
| 평가 방법 | 항목만 | 데이터 버전, seed, threshold, 하드웨어 |
| 알려진 한계 | 일반 문구 | **이 모델의 구체적 실패 slice** |
| 배포 결정 | 항목만 | 담당자, 승인 threshold, rollback 조건 |

**"알려진 한계"가 리포트의 핵심**이다. 일반적인 면책 문구가 아니라 구체적으로 쓴다.

```markdown
❌ "모델이 새로운 공격에 실패할 수 있습니다"
✅ "source=tool slice에서 macro F1 0.578, benign FPR 0.625.
    도구 출력 형태의 정상 문장 절반 이상을 오탐한다.
    도구 출력 검사에 이 모델을 단독으로 쓰면 안 된다."
```

### 참고할 만한 서술 패턴

참고 프로젝트의 민감도 문서는 **3단 구성**으로 되어 있다.

1. **설정 방법** — 실제 JSON 예시
2. **판정 규칙** — 수식과 그 규칙을 고른 이유
3. **실측 권장값 표** — 체크포인트 / 권장값 / **효과** / **비용**

| 체크포인트 | 권장 시작점 | 효과 | 비용 |
|---|---|---|---|
| base 모델 | `{"_default": 0.8}` | FPR 3.6% → 2.1% | recall 35.2% → 28.6% |
| 파인튜닝본 | `{"_default": 0.7}` | FPR 11.0% → 7.1% | recall 89.0% → 84.1% |

**효과와 비용을 항상 같은 행에** 적는다. "FPR을 낮췄다"만 쓰면 recall이 얼마나 떨어졌는지 감춘다.
그리고 모든 권장값에 실측 근거가 붙어 있다 — **임의로 정한 상수가 없다.**

## 4. 문서와 코드는 어긋난다

리포트를 쓸 때 반드시 알아야 할 실무 함정이 있다.

참고 프로젝트의 README에는 API 응답 예시가 이렇게 적혀 있다.

```json
{"jailbreak_detected": true, "score": 0.95, "category": "...", "risk_level": "high"}
```

그런데 **실제 코드의 스키마는 다르다.**

```json
{"isSafe": false, "riskScore": 0.9, "riskType": "A1", "detectionTimeMs": 42.1}
```

필드 이름이 전부 다르다. 문서가 코드보다 오래된 것이다. 이런 **드리프트(drift)**는 어느 프로젝트에나
생긴다. 그래서:

- 리포트에 쓰는 수치와 필드명은 **문서가 아니라 코드·산출물에서** 가져온다
- 자동 생성 가능한 부분은 자동 생성한다(`make_report.py`가 `report.json`을 읽는 이유)
- 손으로 쓴 예시에는 **언제 기준인지** 날짜와 버전을 적는다

## 5. 모델 카드

리포트와 별개로 **모델 카드**를 만든다. 리포트는 "이번 실험 결과"이고, 모델 카드는 "이 모델은 무엇인가"다.

| 항목 | 내용 |
|---|---|
| **Intended use** | 어디에 쓰라고 만든 모델인가 |
| **Out-of-scope use** | 쓰면 안 되는 곳 (여기가 중요하다) |
| **Training data** | 출처, 규모, 생성 방법, 한계 |
| **Metrics** | 어느 데이터에서 얼마인지, 표본 수 포함 |
| **Limitations** | 알려진 실패 slice, 취약한 변형 |
| **재현 명령** | 이 모델을 다시 만드는 정확한 명령 |

**Out-of-scope use**의 예:

```markdown
- 이 모델의 판정을 권한 상승·인증 근거로 사용하는 것
- 도구 allowlist 없이 이 모델만으로 도구 호출을 허용하는 것
- 한국어/영어 외 언어 입력에 사용하는 것
- source=tool 입력을 이 모델 단독으로 판정하는 것 (FPR 0.625)
```

## 6. 이해관계자에게 보고할 때

경영진·고객에게 "탐지율 99%"만 말하면 안 된다. 최소한 다음을 함께 말한다.

| 반드시 함께 말할 것 | 예시 |
|---|---|
| 어느 분포에서 잰 것인가 | "합성 벤치마크 192건 기준" |
| 정상 차단률은 얼마인가 | "정상 문장의 33%를 차단합니다" |
| 어떤 공격을 놓치는가 | "긴 문서 속 인젝션, 대소문자 변형" |
| 표본 수와 불확실성 | "n=24, 신뢰구간 넓음" |
| 이것이 보증하지 않는 것 | "탐지 통과 = 안전이 아닙니다" |

**"탐지율"이라는 단어 자체도 주의해야 한다.** `attack recall`(우리가 잡은 비율)과 `ASR`(실제 시스템에서
공격이 성공한 비율)은 완전히 다른 지표다. 후자는 탐지기만으로 측정할 수 없다.

## 7. 흔한 실수

| 실수 | 왜 문제인가 |
|---|---|
| 최고 점수만 보고 | 나머지 slice의 실패가 숨는다 |
| 표본 수 생략 | n=8의 0.250과 n=800의 0.250은 다른 정보다 |
| 개선만 적고 악화 생략 | 보고서가 아니라 광고가 된다 |
| 한계를 일반 문구로 | "실패할 수 있음"은 아무 정보가 아니다 |
| 문서 예시를 코드 확인 없이 인용 | 드리프트로 틀린 스키마를 전파 |
| 벤치마크를 반복 튜닝 대상으로 | 벤치마크가 오염되어 비교 가치를 잃는다 |

마지막이 특히 중요하다. **공개 벤치마크는 반복 사용으로 오염된다.** 여러 팀이 같은 벤치마크를 보며
튜닝하면, 그 벤치마크 점수는 일반화 능력이 아니라 "그 벤치마크에 맞춘 정도"를 재게 된다.
그래서 자체 검수 holdout을 별도로 유지한다.
