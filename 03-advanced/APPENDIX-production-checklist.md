# 부록 · 운영 적용 체크리스트

이 커리큘럼을 끝내고 실제 시스템에 적용할 때 확인할 항목이다. 순서는 대략 배포 전 →
배포 시점 → 운영 중 → 사고 대응이다.

**전제**: 탐지기는 방어층 **하나**다. 아래 항목 중 상당수는 탐지기가 완전히 실패해도
시스템이 버티게 만드는 것들이며, 그것이 핵심이다.

---

## 1. 신뢰 경계 — 탐지기보다 먼저

탐지 성능과 무관하게 반드시 성립해야 하는 것들이다. 여기가 무너지면 탐지기가 아무리
좋아도 소용없다.

- [ ] 입력 출처(`source`)는 사용자가 제공한 문자열이 아니라 **서버가 신뢰 경계에서 부여**한다.
      클라이언트가 `source: "system"`이라고 주장할 수 있으면 그 필드는 아무 의미가 없다.
- [ ] 외부 문서와 도구 출력은 기본적으로 신뢰하지 않는다. 검색 결과 안의 문장은
      데이터이지 지시가 아니다.
- [ ] 도구에는 최소 권한, allowlist, 인자 검증을 적용한다. **탐지 결과와 무관하게** 적용한다.
- [ ] 분류 결과를 권한 상승의 근거로 사용하지 않는다. "BENIGN이니까 이 도구를 허용"은 금지다.
- [ ] 민감 작업에는 사람 승인 또는 별도의 deterministic policy를 둔다.
- [ ] **탐지기를 비활성화해도 핵심 권한 경계가 유지되는지 장애 훈련으로 확인한다.**
      훈련을 해보지 않았다면 이 항목은 체크된 것이 아니다.

## 2. 판정 불가를 안전으로 바꾸지 않는다 (fail-closed)

- [ ] 입력이 max_len을 넘으면 잘라서 판정하지 않는다. 거부하거나 chunk로 나눠 판정한다.
- [ ] 추론 백엔드 오류·타임아웃은 통과가 아니라 에러로 처리하고, 상위에서 정책에 따라 차단한다.
- [ ] 모델 출력이 스키마에 맞지 않으면 통과가 아니라 차단이다.
- [ ] fail-closed의 대가를 미리 계산한다. 백엔드가 죽으면 **전체 트래픽이 막힌다.**
      그 상태를 견딜 수 있는지, 아니면 degraded 모드(규칙만 사용)가 필요한지 정한다.

## 3. 배포 전 검증

- [ ] 회귀 게이트가 CI에 있고, 실제로 실패하는 것을 한 번 확인했다.
      (`.github/workflows/ci.yml`, `03-advanced/03-hybrid-gates/quality_gate.py`)
- [ ] 회귀 방지선과 운영 목표치를 구분해 적어 두었다. 둘을 섞으면 CI가 늘 빨간불이라
      아무도 보지 않게 된다.
- [ ] 표본 수와 신뢰구간을 함께 기록했다. 구간이 겹치는 두 모델의 차이는 개선이 아니다.
- [ ] seed 편차를 측정했고, 개선폭이 그보다 크다는 것을 확인했다.
- [ ] 슬라이스별로 확인했다: 언어, `source`, 길이, 표면 변형. 전체 평균은 최악의 슬라이스를 가린다.
- [ ] 하드 네거티브 전용 세트에서 benign FPR을 따로 쟀다.
- [ ] threshold는 dev에서 정했고 test는 최종 확인에 한 번만 썼다.
- [ ] 모델 카드가 있다: 학습 데이터 출처와 버전, 알려진 한계, 평가 조건, 담당자.

## 4. 탐지와 정책의 분리

- [ ] 탐지 엔진은 판정(라벨 + 점수)만 내고, 차단 여부는 정책 층이 정한다.
- [ ] 모델 / threshold / 정책을 **각각** 버전 관리한다.
- [ ] threshold 변경은 모델 재배포 없이 가능하다.
- [ ] threshold 변경에 승인 절차가 있다. 누가 바꿀 수 있고, 누가 승인하며, 어디에 기록되는가.
- [ ] 정책 변경도 롤백 가능하다. "threshold를 0.6으로 내렸더니 review 큐가 터졌다"에서
      즉시 되돌릴 수 있어야 한다.
- [ ] **모델을 바꾸면 threshold를 dev에서 다시 정한다.** 같은 0.8이 다른 지점을 가리킨다
      (`02-intermediate/05-error-analysis/calibration.py`).

## 5. review 큐 운영 — 사람이 실제로 볼 수 있는가

`allow / review / block` 3단계 정책은 review를 **사람이 처리한다**는 전제 위에 있다.
그 전제를 검증하지 않으면 review는 사실상 allow다.

- [ ] review 비율을 추정했다. 하루 요청 N건 중 몇 건이 큐에 들어가는가.
- [ ] 그 양을 처리할 사람이 있는가. 1건당 몇 초가 걸리고, 하루 몇 시간이 필요한가.
- [ ] 처리 못 한 review는 어떻게 되는가. 시간이 지나면 allow인가 block인가.
      **정해두지 않았다면 십중팔구 allow다.**
- [ ] 검토자에게 판정 근거(매칭된 규칙, 점수, 유사 사례)를 함께 보여주는가.
- [ ] 검토자의 판정이 데이터셋으로 돌아오는가 (아래 7번).

## 6. 로깅과 개인정보

- [ ] 원문 로그 대신 필요한 최소 필드만 보존한다.
- [ ] 접근 권한과 보존 기간을 통제한다.
- [ ] 보존 정책과 개인정보 규정을 법무/보안과 확인했다.
- [ ] 로그에서 시스템 프롬프트와 비밀이 제외되는지 확인했다.
- [ ] 학습에 재사용할 로그는 별도 동의·검토 경로를 거친다.

## 7. 피드백 루프 — 운영 데이터를 데이터셋으로

이것이 없으면 모델은 배포 시점에 멈춰 있고, 공격자만 계속 학습한다.

- [ ] 사용자가 오탐을 신고할 수 있는 경로가 있다.
- [ ] 신고와 review 판정이 **라벨 후보로 수집**된다.
- [ ] 수집된 후보를 어노테이션 가이드에 따라 검수하는 주기가 있다.
- [ ] 검수된 데이터가 다음 데이터셋 버전에 들어가고, 그 버전으로 재학습·재평가한다.
- [ ] 운영에서 온 샘플이 test에 들어가 누수를 만들지 않도록 `group_id` 규칙을 적용한다.
- [ ] 재학습 주기와 트리거를 정해 두었다 (정기 / drift 감지 시 / 신규 공격 유형 발견 시).

## 8. 모니터링

- [ ] 차단률과 review 비율의 시계열. 갑작스러운 변화는 공격이거나 우리 쪽 버그다.
- [ ] `source` / `language` / 길이 분포의 drift. 학습 분포에서 멀어지면 성능 보증이 깨진다.
- [ ] 샘플링된 오탐/미탐을 주기적으로 사람이 읽는다. 지표만 보면 새 공격 유형을 놓친다.
- [ ] 추론 지연시간 p50/p95와 에러율.
- [ ] 요청당 원가. 트래픽이 늘면 여기서 먼저 문제가 생긴다.
- [ ] 알림 기준이 있다: 어떤 값이 얼마나 변하면 누구에게 알리는가.

## 9. 사고 대응

- [ ] 우회 사례가 보고되었을 때의 절차가 있다: 재현 → 영향 범위 → 임시 완화 → 데이터 반영.
- [ ] 임시 완화 수단이 있다. threshold 상향, 특정 패턴 즉시 차단, 해당 기능 비활성화.
- [ ] 즉시 rollback이 가능하다. 모델·threshold·정책 각각.
- [ ] 사고 후 회고에서 **왜 벤치마크가 이것을 잡지 못했는지**를 묻고, 그 답을 벤치에 추가한다.

## 하지 말아야 할 것

| 하지 말 것 | 왜 |
|---|---|
| 탐지 통과를 "안전 확인"으로 문서화 | 탐지기는 안전을 증명하지 못한다. 위험 신호가 없었을 뿐이다 |
| 벤치마크 숫자를 제품 성능으로 홍보 | 합성 데이터와 작은 고정 벤치는 운영 분포를 대표하지 않는다 |
| 탐지 결과로 권한을 부여 | 모델 하나의 오판이 권한 상승으로 이어진다 |
| threshold를 test에서 튜닝 | test는 최종 확인용이다. 한 번 보고 나면 그 수치는 낙관적이다 |
| 공격 데이터만 늘려 recall 개선 | benign FPR이 조용히 올라간다. 두 지표는 함께 움직인다 |
| 지표 하나만 알림에 연결 | recall만 보면 전부 차단하는 고장을 정상으로 읽는다 |
